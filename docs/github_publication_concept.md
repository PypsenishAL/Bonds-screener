# Публикация данных для Streamlit через GitHub

Дата: 2026-10-30. Статус: концепция уточнена по утверждённому ТЗ; реализация и Goldfish-ревью не проводились.

Окончательные требования: [ТЗ публикации](designs/github-publication/github_publication.md).

## Основная идея

На ПК остаются сбор данных, обновление истории и все расчёты. GitHub хранит
согласованный опубликованный комплект. Streamlit читает готовые результаты.
Это сохраняет действующее разделение сборщика, анализа и интерфейса.
Полная историческая база остаётся локально: самостоятельная публикация истории
пользователю не нужна. Облако получает только необходимые приложению данные.

В текущем проекте `main.py` уже обновляет инициализированную историю и догружает
пропущенные опубликованные даты. `history.py` нужен для первой полной загрузки
и явной пересборки. Новая работа прежде всего касается публикации и запуска
существующих этапов в нужном порядке.

## Предлагаемый ежедневный цикл

1. Собрать дневные данные и обновить локальную историю существующим механизмом.
2. Запустить `analyze_spreads.py` на обновлённых данных.
3. Проверить комплект: статусы завершения, даты, схемы, связи и контрольные суммы.
4. Подготовить только предназначенные для публикации файлы.
5. Опубликовать согласованный комплект дневных данных и готового анализа.
6. Приложение загружает завершённую публикацию и показывает её дату.

Этапы выполняются последовательно. «Одновременно» означает один пользовательский
запуск, который завершается после выполнения всей цепочки.

## Структура и доставка

Сохранить `app.py`, `requirements.txt`, `moex_bonds/`, `config/`, `static/`,
`.streamlit/` и существующие локальные области `data/`.
Облачный комплект содержит необходимые части `daily_data/` и `spread_analysis/`,
без полной `history_data/`. Двух CSV из примера недостаточно для текущего приложения.
Точный список таблиц и сопровождающих файлов определить по читателям в коде.

Код приложения размещается в репозитории, подключённом к Streamlit Community Cloud.
Для данных хранится один актуальный комплект, без ежедневного архива снимков.
Исторические графики внутри актуального анализа сохраняются: они не требуют
хранения всех предыдущих публикаций. Выбор прошлых публикаций в облачной версии
при таком ограничении будет недоступен; это следствие предлагаемого ограничения хранения.

Обычное ежедневное обновление файлов через commit и push сохраняет их старые
версии в Git. Поэтому оно не обеспечивает ограниченный размер репозитория.
На первом этапе согласован обычный commit и push через HTTPS из текущей папки
проекта в `https://github.com/PypsenishAL/Bonds-screener.git`.
Внутри проекта `data/published/` содержит только актуальный комплект для приложения.
GitHub Releases не используются; размер комплекта и рост Git измеряются отдельно.
Публикация должна исключать смешение файлов разных расчётов.

Существующий `.gitignore` исключает `data/`: понадобятся точечные исключения
для утверждённого комплекта. Архивы, окружения, временные файлы, секреты и
сырой аудит в комплект не включать. Локальный аудит сохраняется.

## Условия сохранения методологии

- Не менять фильтры, расчёты, корзины, веса и правила классификации.
- Сохранить ключ истории `SECID + BOARDID + TRADEDATE`, реальные торговые даты
  и явные причины отсутствия данных; не заполнять пропуски выдуманными значениями.
- При ошибке любого обязательного этапа не публиковать новый комплект.
- Ошибка push сохраняет локальный результат; повторяется доставка готового
  комплекта, без обязательного повторного сбора и расчёта.
- Повторный запуск за ту же дату не создаёт дубли истории.
- Автопубликация затрагивает только утверждённые файлы данных, без чужих
  незакоммиченных изменений; force push не использовать.

## Ограничения хранения

ПК нужен для обновления данных, но его выключение не должно мешать облачному
приложению показывать последнюю опубликованную версию.
GitHub подходит для начального объёма, однако ежедневные версии больших CSV
увеличивают репозиторий. Текущая база истории занимает около 14,4 МБ,
а одна таблица сравнения — около 22,6 МБ; снимки анализа дублируют часть данных.
Не накапливать ежедневные снимки в облачном комплекте. Не загружать в память
Streamlit полную исходную историю и не создавать неограниченный кеш версий.
Размер CSV на диске не равен потреблению памяти: до публикации проверить
пиковую память приложения при чтении реального комплекта.
Локальная историческая база продолжает накапливаться по действующим правилам;
её не обрезать автоматически ради ограничения облачного хранилища.
