# ТЗ: публикация данных для онлайн-приложения Streamlit

**Дата:** 2026-10-30  
**Состояние:** утверждено владельцем; финальная сверка выполнена.  
**Основание:** `docs/github_publication_concept.md` и последующие уточнения пользователя в чате.

## Проблема

Приложение читает локальные результаты сбора и анализа. Для его работы
в Streamlit Community Cloud нужно доставлять необходимые файлы на GitHub
после локального обновления данных. Ручное копирование файлов после каждого
дневного запуска не должно требоваться.

Пользователю нужна работа приложения, а не открытый архив исходной базы.
Нужно исключить ненужное дублирование данных и накопление ежедневных снимков
в текущем облачном комплекте; потребление оперативной памяти проверить отдельно.

## Обзор решения

Исторический скрипт создаёт полную базу на ПК. Ежедневный запуск собирает
дневные данные, обновляет локальную историю, выполняет существующий анализ,
проверяет результат и публикует необходимые приложению файлы через обычные
Git commit и push. Этапы выполняются последовательно в рамках одного запуска.

Полная исходная историческая база остаётся локально. В облако передаются
актуальные готовые результаты анализа и необходимые дневные данные с
сопровождающими файлами. Исторические ряды для графиков остаются в результатах
анализа. Streamlit читает завершённый комплект и не запускает сбор или расчёты.

Последнее согласованное уточнение заменяет предложение о GitHub Releases
в исходной концепции: на первом этапе используется обычный Git push.
Перезапись файлов не удаляет старые версии из истории Git, поэтому ограниченный
размер репозитория не обещается. Размер публикации и рост репозитория измеряются.

## Цели

1. Обеспечить работу опубликованного приложения с актуальными данными без
   зависимости от доступности ПК после успешной публикации.
2. Выполнять ежедневное обновление и доставку данных одним пользовательским
   запуском, сохраняя первоначальную сборку истории отдельным действием.
3. Передавать согласованный комплект одной публикации: дневные данные,
   анализ и необходимые метаданные должны соответствовать друг другу.
4. При ошибке обязательного этапа не заменять последнюю опубликованную версию.
   При ошибке отправки сохранять локальный комплект для повторной доставки.
5. Сохранить методологию, численные результаты, фильтры, идентичность записей,
   реальные торговые даты и явные состояния отсутствующих данных.
6. Хранить в текущем облачном комплекте одну актуальную публикацию без полной
   исходной истории, сырого аудита, архивов и временных файлов. Ограничение
   облачного комплекта не обрезает локальную историческую базу.
7. Проверить запуск приложения на реальных опубликованных данных, размер
   комплекта и пиковое потребление памяти; не считать размер CSV оценкой RAM.

## Вне объёма работ

- Изменение аналитической методологии, инвестиционных правил и дизайна интерфейса.
- Перенос сборщиков или расчётов в Streamlit, GitHub Actions или отдельный сервер.
- Публикация полной исходной исторической базы как самостоятельного продукта.
- Облачный архив всех прошлых публикаций; выбор прошлых дат публикации
  не входит в обязательный сценарий облачной версии. Исторические графики
  внутри актуальной публикации сохраняются.
- GitHub Releases, LFS, внешняя база данных и автоматическая очистка истории Git.
- Перенос всей структуры проекта, исходных архивов и локальных окружений.

интерактивного запроса; отсутствие доступа завершает публикацию с понятной
ошибкой, без ожидания ввода и без вывода секретов.

Пароли, токены и закрытые ключи не передаются в чат, не записываются в код,

## Техническая часть: ежедневное обновление и публикация

Раздел утверждён владельцем, включая интерфейс запуска, состав комплекта,
порядок отправки и обработку ошибок.

### Поток данных

```text
history.py → локальная история: первая загрузка / явная пересборка
                             ↓
main.py --publish → дневной сбор и догрузка истории
                  → analyze_spreads.py
                  → проверка и подготовка комплекта
                  → commit только разрешённых файлов данных
                  → push в Bonds-screener
                  → Streamlit читает опубликованный комплект
```

Предлагаемый пользовательский запуск — `python main.py --publish`.
Обычный `python main.py` сохраняет существующее поведение без отправки в GitHub.
В режиме публикации первоначальная история должна быть заранее создана:
`not_initialized` является ошибкой, а не поводом незаметно собрать полную историю.
Частичный сбор по списку SECID и режим без дневной книги не публикуются.

Успех проверяется по коду завершения и манифестам: дневной сбор и экспорт
завершены, история синхронизирована до дневной даты, анализ завершён на тех же
входах. Одного успешного завершения процесса недостаточно. Существующие состояния
недостаточности данных внутри корректно завершённого анализа остаются допустимы.

### Отделение публикуемых файлов от локальных накоплений

Внутри текущего проекта предлагается `data/published/` — небольшой комплект
для отправки. Это копия только выбранных готовых файлов данных, а не отдельное
приложение и не отдельный Git-репозиторий. Она нужна, чтобы не удалять локальные
снимки и накопленные таблицы ради ограничения облачного комплекта.

Исходные `data/daily_data`, `data/history_data`, `data/spread_analysis` остаются
под существующими правилами локального хранения и не отслеживаются Git.
В `.gitignore` открывается только `data/published/` с явно разрешённым составом.
Устаревшие файлы удаляются только внутри этого публикуемого комплекта,
после проверки разрешённых абсолютных путей; исходные папки не очищаются.

Состав публикации:

| Путь относительно `data/published/` | Назначение |
|---|---|
| `publication_manifest.json` | Дата, ID анализа, версия комплекта, относительные пути, размеры и SHA-256 всех файлов комплекта |
| `daily_data/daily/bonds_daily.xlsx` | Дневная выгрузка и дополнительные поля интерфейса; без повторного формирования XLSX |
| `daily_data/run_manifest.json` | Состояние дневного сбора и привязка даты |
| `daily_data/cbr_zcyc.csv` | Данные кривой ЦБ за дату анализа, если источник доступен |
| `daily_data/_support/cbr_zcyc_status.json` | Состояние кривой ЦБ, включая явную недоступность |
| `spread_analysis/run_manifest.json` | Маркер завершённой публикации анализа |
| `spread_analysis/snapshots/<дата>/run_manifest.json` | Метаданные актуального снимка |
| `spread_analysis/snapshots/<дата>/summary.csv` | Сводка |
| `spread_analysis/snapshots/<дата>/metrics.csv` | Сохранённые метрики |
| `spread_analysis/snapshots/<дата>/comparison_history.csv` | Исторические ряды актуального анализа |
| `spread_analysis/snapshots/<дата>/basket_members.csv` | Составы и веса корзин |
| `spread_analysis/snapshots/<дата>/recovery_episodes.csv` | Сохранённые эпизоды восстановления |
| `spread_analysis/snapshots/<дата>/candidate_exclusions.csv` | Сохранённые причины исключений |

Корневые накопительные CSV анализа не копируются: UI читает таблицы из снимка.
Сырой аудит, полная история, отчёты разработки, окружения и архивы не отправляются.
Дополнительная конвертация дневного XLSX в CSV для работы приложения не требуется.

Недоступность необязательного источника ЦБ не подменяется старой кривой:
публикуется его явный статус, а файл данных не включается. Обязательные файлы
анализа и дневная книга должны быть корректны. Точные допустимые статусы
необязательных источников закрепить в подробном плане после проверки сборщика.

### Целостность и переносимость

Комплект сначала готовится во временной локальной папке вне отслеживаемых данных.
До замены `data/published` проверяются SHA-256, размеры, даты, ID расчёта,
схемы таблиц и фактическое чтение существующим валидатором UI. При копировании
проверяется отсутствие изменения исходной публикации. Блокировка единого запуска
исключает одновременную работу двух процессов обновления и отправки.

Проверено ограничение текущего кода: привязка дневной книги использует пути
из `source_sha256`, которые могут содержать абсолютный путь Windows. На Linux
Streamlit и в каталоге `data/published` такой путь не совпадёт с новым расположением.
Нужно добавить переносимую привязку по полному относительному пути внутри
комплекта и SHA-256. Совпадения одного имени файла недостаточно.
Сохранённые исходные манифесты и численные результаты не переписываются;
новый манифест публикации связывает фактические байты с исходным анализом.

### Работа Streamlit

Облачный запуск использует `data/published`: приложение выбирает единственный
актуальный снимок, проверяет манифест комплекта и читает существующие таблицы.
Приложение не обращается к MOEX и не читает локальную историческую базу.
Отдельные HTTP-запросы за каждым CSV не добавляются: данные доступны в версии
репозитория, которую получил Streamlit Community Cloud.

Локальный режим сохраняет чтение исходных рабочих папок; режим опубликованных
данных выбирается явно настройкой запуска. При повреждённой публикации нельзя
незаметно переключиться на исходные локальные данные. В интерфейсе остаются
дата анализа и причины недоступности данных. Новые результаты становятся видны
после обновления облачного развёртывания и повторного выполнения приложения;
немедленное обновление уже открытых страниц не обещается.

### Git и авторизация

При первоначальной настройке проверяются содержимое удалённого репозитория,
его ветка по умолчанию, права записи, автор коммитов и связь `origin` с точным
HTTPS-адресом. Если репозиторий пуст, создаётся согласованная при настройке ветка;
если уже содержит файлы, они сначала сопоставляются с проектом без перезаписи.
Первичная публикация кода и настройки Streamlit — отдельный проверяемый шаг.

Ежедневная отправка не коммитит код автоматически. До сбора проверяются
отсутствие незавершённых изменений отслеживаемого кода и посторонних файлов
в индексе, правильность ветки и отсутствие чужих неопубликованных коммитов.
Подготовка к коммиту затрагивает только разрешённые файлы `data/published`;
использовать `git add .`, автоматический stash, reset, rebase или force push нельзя.

Перед отправкой выполняется fetch без изменения рабочих файлов.
Локальная и удалённая ветки должны совпадать по исходному коммиту.
При отставании или расхождении публикация останавливается с указанием причины;
автоматическое слияние не выполняется. Если remote изменился после проверки,
отказ обычного push также считается ошибкой доставки, а не поводом force push.

Отправка не должна открывать запрос авторизации во время автоматического запуска:
настроенные учётные данные используются неинтерактивно с ограничением времени.
При отсутствии доступа выводится действие для пользователя — повторить вход
вручную под той же учётной записью Windows. Секреты в лог не выводятся.

### Повторная отправка и ограничения хранения

При ошибке push сохраняются подготовленный комплект и локальный коммит.
Отдельный режим повторной отправки проверяет тот же комплект и ожидаемый коммит,
сверяет remote и не запускает сбор или анализ повторно. Потеря ответа после
успешного push разрешается проверкой удалённого SHA, а не новым коммитом.
Неизменный комплект не создаёт пустой коммит. Повторный расчёт может иметь
другой ID запуска и считается другой публикацией даже при равных числах.

В рабочем облачном комплекте остаётся один снимок; локальная история продолжает
накапливаться по прежним правилам. Git сохраняет прошлые коммиты. В результат
публикации записываются размер комплекта, крупнейший файл и локальный размер
объектов Git; последний не объявляется точным размером хранения на GitHub.
До первой отправки проверяются актуальные ограничения GitHub на размер файлов.
Потребление RAM проверяется при открытии реального комплекта в Streamlit;
не добавляется неограниченный кеш разных публикаций.

## Рассмотренные альтернативы

Этот раздел фиксирует решения обсуждения; новые архитектурные решения
не добавляются. Отказ от варианта относится к текущему этапу проекта.

### Публиковать полную исходную историческую базу

Такой вариант был в первоначальном запросе и позволял бы скачивать исходную
историю с GitHub. После уточнения потребности он исключён: пользователю нужна
работа приложения, а не отдельная публикация базы. Приложение читает готовые
результаты анализа, поэтому отправка исходной истории добавляет объём без
необходимости для согласованного сценария. История остаётся на ПК;
исторические ряды графиков входят в актуальный анализ и сохраняются в облаке.

### Хранить крупные данные в GitHub Releases

Вариант предлагался для ограничения накопления версий данных в истории Git.
Он потребовал бы отдельного скачивания, выбора версии и очистки старых архивов.
Владелец согласился начать с обычной замены файлов через commit и push.
Поэтому Releases исключены из первой реализации. Компромисс принят явно:
один текущий комплект не ограничивает размер истории Git. Размеры измеряются;
новая схема хранения при необходимости потребует отдельного решения.

### Использовать отдельный локальный клон для публикации

Он отделяет автоматическую отправку от незавершённой разработки в исходной
папке, но создаёт ещё одну копию приложения и требует поддерживать её код
согласованным с данными. Владелец выбрал текущую папку проекта.
Следствие выбора: автоматическая отправка останавливается при посторонних
подготовленных изменениях, незавершённых изменениях кода или расхождении веток.

### Авторизовать отправку через SSH

SSH позволяет отправлять изменения с локальным ключом, но требует настройки
ключа и его доступности в контексте автоматического запуска. Владелец выбрал
HTTPS; на ПК уже настроен Git Credential Manager. В первой реализации
используется его сохранённый доступ, без отдельной настройки SSH.

оно читает уже созданную книгу через установленный `openpyxl`.
Файлы исходного кода не удаляются.

### Интерфейсы запуска и предварительные условия

- `python main.py` — прежний локальный сбор без публикации.
- `python main.py --publish` — полный дневной цикл с публикацией.
- `python main.py --publish-retry` — доставка сохранённой попытки без сбора и анализа.
- `python history.py` — первоначальная история или явная пересборка, без Git-отправки.

В режиме публикации разрешены существующие `--date`, `--timeout`, `--pause`.
`--secids`, `--no-daily`, `--csv-only` и нестандартные `--output`/`--history-output`
отклоняются до изменения данных. Режим повтора не принимает параметры сбора.
В тестах пути передаются внутренним функциям, не через производственные исключения.

Перед сбором проверить историю `status=ok` с непустым подтверждённым календарём,
рабочий Git root, точный `origin`, выбранную ветку, автора коммитов, отсутствие
изменений отслеживаемого кода и пустой посторонний индекс. Ранее подготовленный,
но не отправленный комплект блокирует новый полный цикл до разбора его состояния.
Fetch не меняет рабочие файлы. Невозможность проверить remote останавливает цикл
до сбора; право записи окончательно подтверждается настоящим push при подключении.

### Сбор, анализ и проверка статусов

Сценарий вызывает существующий `run(args)` сборщика, затем `run_analysis` с
явными путями дневной книги, истории, анализа и выбранной датой. Фильтры и
методология не дублируются в новом сценарии.

Учитывается существующее поведение: сборщик возвращает код 4 при проблемах
с необязательными источниками ЦБ. В новом сценарии только этот код может быть
допустим при одновременно успешных обязательных статусах: `collection_status=ok`,
`daily_export.status=ok`, `xlsx_status=ok`, `history_update.status=ok`.
Другие ненулевые коды останавливают цикл. Дополнительно проверяются исторический
манифест и синхронизация до дневной даты. Семантика обычного сборщика не меняется.

Для КБД допустимы конечные статусы `ok`, `unavailable`, `error` за правильную дату.
`pending`, `not_requested`, отсутствие или противоречие статусов являются ошибкой
подготовки комплекта. При `ok` обязательны 12 корректных сроков кривой за ту же дату;
при остальных допустимых статусах кривая не включается, причина сохраняется.
Неполученная RUONIA не блокирует комплект: текущий UI её не читает, а исходный
дневной манифест сохраняет её состояние. Это не разрешает игнорировать ошибки MOEX,
дневного экспорта или истории под видом отсутствия данных ЦБ.

Перед копированием проверяются совпадение даты и ID корневого/датированного анализа,
отсутствие активных писателей и неизменность входных хешей, сохранённых анализом.
Копирование выполняется при захваченных существующих блокировках источников;
порядок захвата фиксирован: дневные данные, история, анализ. Блокировки не
удерживаются во время сетевых Git-операций. После копирования хеши сверяются снова.

### Переносимый манифест и чтение

Контракт `publication_manifest.json`:

- `publication_schema_version=1`, `status=ok`, `analysis_date`, `analysis_run_id`;
- `files`: отображение полного относительного POSIX-пути в `sha256` и `size_bytes`;
- `source_bindings.daily_workbook`: относительный путь книги в комплекте,
  исходный полный ключ из `source_sha256` анализа и SHA-256 исходной книги;
- `source_statuses.cbr_zcyc`: дата, конечный статус и сохранённая причина недоступности;
- `total_size_bytes`: сумма размеров файлов из `files`, без самого манифеста.

В манифест не включаются время текущей проверки, токены или собственный хеш файла:
один и тот же исходный комплект должен давать одни и те же байты манифеста.
`files` содержит ровно разрешённый набор; порядок сериализации детерминирован.
Абсолютные пути назначения, `..`, ссылки, junction и выход за корень комплекта
отклоняются. Исходный Windows-путь в `source_bindings` — только ключ происхождения,
он не используется как путь для чтения на сервере.

При подготовке текущий исходный путь книги сопоставляется с точным ключом
`source_sha256`, включая уже поддерживаемую привязку к прежнему расположению
рабочих данных. В облаке проверяется равенство сохранённого ключа и хеша из
исходного манифеста анализа, хеша из `files` и фактических байтов книги.
Не допускаются поиск по одному basename или изменение исходного манифеста.

Сценарий подготовки прогоняет через существующие функции UI временный комплект:
снимок, дневную книгу и доступную кривую. Новый манифест проверяется дополнительно,
а не заменяет проверки содержимого таблиц. В опубликованном режиме ошибка любого
обязательного файла останавливает чтение комплекта, без подстановки локальных данных.

Блокировка сценария `.work/publication/update.lock` охватывает весь полный цикл
или повторную отправку. Устаревшая блокировка не удаляется автоматически:
сообщение содержит PID/этап и действие для ручной проверки.
Временная копия создаётся в `.work/publication/staging/`, затем проверенный
комплект заменяет `data/published` с возможностью восстановления предыдущей
локальной копии при сбое. Временные/резервные каталоги очищаются только после
проверки абсолютных путей внутри `.work/publication`.

### Git-коммит, состояние попытки и повтор

В `.work/publication/state.json` хранится локальное состояние попытки:
этап, remote URL, ветка, исходный SHA, идентификатор анализа, SHA манифеста,
ожидаемый Git tree подготовленного комплекта и SHA созданного коммита.
Состояние записывается безопасной заменой файла до перехода к следующему этапу;
оно не коммитится. Журнал `.work/publication/last_result.json` содержит последний
результат, этап ошибки, размеры и проверенный удалённый SHA; токенов там нет.

Git запускается списком аргументов с фиксированным root, не через shell.
Отключаются интерактивные Git/GCM-запросы, вывод ограничивается и очищается от
учётных данных. Все сетевые операции имеют настроенный таймаут.
Разрешены только HTTPS URL без встроенных логина/пароля/токена.

Перед созданием коммита проверяется полный набор staged-путей: добавления,
изменения и удаления только из разрешённого комплекта, включая удаление
предыдущего датированного снимка. Игнорируемые исходные данные не добавляются
через `--force`; правила `.gitignore` и точный список путей должны быть достаточны.
Коммит содержит дату анализа и ID публикации, push задаёт конкретную ветку.
Нет разницы по байтам — нет нового коммита. Пустой коммит не создаётся.

Этапы состояния: `prepared`, `committed`, `push_pending`, `published`.
Если процесс оборвался сразу после коммита, но до сохранения его SHA, повтор
может принять только единственный новый коммит с ожидаемыми parent SHA, tree,
путями и ID публикации. При любой неоднозначности он останавливается.

При повторе проверяются неизменность комплекта и отсутствие посторонних изменений.
Если remote SHA уже равен SHA попытки, отправка считается подтверждённой.
Если remote является потомком этого SHA, попытка отмечается как ранее доставленная,
но сообщение отдельно указывает, что удалённая ветка уже обновлена дальше.
Если remote остался на исходном SHA, повторяется обычный push того же коммита.
При расхождении веток или неизвестных локальных коммитах автоматическое
восстановление не выполняется. Новый сбор не начинается до разрешения ситуации.

Коды завершения нового сценария: 0 — успех или отсутствие изменений;
20 — настройки/предварительные условия; 21 — обязательный сбор/история;
22 — анализ/проверка комплекта; 23 — Git/доставка; 24 — занятая блокировка.
В сообщении дополнительно указывается конкретный этап. Старые коды обычного
сборщика остаются прежними. Локальный результат не объявляется опубликованным
до подтверждения удалённого коммита.

### Первоначальное подключение и ввод в работу

1. Проверить фактическое содержимое и ветку целевого remote. Непустой репозиторий
   не считать пустым по отсутствию ответа, ошибке сети или авторизации.
2. Настроить Git в текущей папке, `origin`, ветку и автора. Существующие удалённые
   файлы сначала сопоставить с локальными, без удаления или force push.
3. Выполнить первоначальный вход через браузер с GCM от имени Windows-пользователя
   будущего запуска. Не помещать учётные данные в проект или настройки Streamlit.
4. Подготовить первый комплект на существующих корректных локальных данных,
   проверить состав отслеживаемых файлов и создать отдельно проверяемую первую
   публикацию кода и данных. В неё включаются только исходники, необходимые
   настройки, зависимости, статические ресурсы и утверждённый комплект.
5. Подключить Community Cloud к фактической ветке и `app.py`; установить
   `BONDS_DATA_MODE=published` в настройках secrets, выбрать совместимую версию
   Python и проверить установку существующих зависимостей.
6. Проверить опубликованное приложение, затем реальный полный дневной цикл.
   Планировщик Windows при необходимости вызывает ту же команду; отдельный
   механизм расписания в исходный код не добавляется.

### Проверки и критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Состав комплекта | Ровно утверждённые файлы одной даты; нет исходной истории, накопительных корневых CSV, аудита, секретов и предыдущих снимков. |
| Сохранность источников | Подготовка/повторная отправка не меняют хеши исходных истории, анализа и дневной книги; полный цикл изменяет их только существующими сборщиком и анализом. |
| Перенос на другой корень/ОС | Те же байты комплекта читаются с другим корнем; Windows-ключ источника не становится путём чтения на Linux. Подмена книги или полного пути привязки отклоняется. |
| Нарушение целостности | Изменённый CSV/XLSX, чужая дата/ID, лишний файл, traversal или ссылка не допускаются к коммиту и чтению UI. |
| Состояния источников | Ошибка истории останавливает публикацию; `not_initialized` не запускает скрытый сбор. Для ЦБ доступны только описанные конечные статусы, старая кривая не подставляется. |
| Сбой каждого этапа | До Git-коммита remote не меняется; после ошибки push сохранены точный комплект и повторяемая попытка. |
| Реальные Git-сценарии автономно | Временный bare remote: успешная отправка, отсутствие изменений, потеря ответа после push, сбой после commit, remote впереди/разошёлся, посторонний staged-файл, изменённый код, несовпадающий origin. |
| Безопасность удаления | Старый снимок удаляется только из `data/published`; исходные локальные снимки и файлы за пределами разрешённых каталогов сохраняются. |
| Совместимость приложения | Списки, карточки, история, окна 90/150, составы корзин, причины исключений и восстановления соответствуют тем же локальным результатам. Смена публикации не оставляет выбранную дату отсутствующего снимка. |
| Размеры и RAM | В отчёте фактический размер комплекта, крупнейшего файла, локальных объектов Git и пик RSS процесса Streamlit. Размер CSV не подставляется вместо RSS. |
| Настоящая отправка | На реальном репозитории проверены HTTPS и право записи; удалённый SHA подтверждён. Автономный bare remote этого не доказывает. |
| Облачная приёмка | Приложение открывается на Community Cloud, показывает дату публикации и работает без исходной истории и доступности ПК. Локальный запуск не считается облачной проверкой. |

Автономная команда: `python -m unittest discover -s tests -t .` из корня проекта.
Тесты работают во временных папках и локальных Git-репозиториях, без настоящего
GitHub, сетевого сбора и записи в рабочую историю. Проверка режима published
на реальных данных выполняется отдельно в чистой временной копии комплекта.

Перед первым live push проверяются актуальные ограничения GitHub на размер
файлов. Пиковая память проверяется в Linux-окружении на реальном комплекте,
включая чтение, валидацию, переключение окон и последовательную смену нескольких
публикаций. Используется измерение процесса, включая дочерние процессы при наличии,
а не оценка по pandas или размеру CSV. Число/модель одновременных сессий и
фактический предел выбранного размещения записываются рядом с результатом;
успех одной сессии не доказывает работу при произвольной нагрузке.
При нехватке памяти реализация не принимается; оптимизация чтения должна
сохранять состав данных и аналитическую методологию.

Подключение, реальный push и облачная приёмка выполняются на этапе реализации.
В этом черновике они не считаются проведёнными. Конечные SHA и URL развёрнутого
приложения добавляются в отчёт реализации, а не выдумываются заранее.

## Финальная сверка с концепцией и уточнениями

Сверка выполнена с `docs/github_publication_concept.md` и последующими
явными решениями владельца в чате. Неразрешённых расхождений с согласованными
требованиями не осталось.

| Пункт | Основание и принятое решение |
|---|---|
| Хранение крупных файлов | Концепция предлагала «кандидат — отдельный архив публикации в GitHub Releases». Позднее владелец согласился начать с обычного `git push`; ТЗ следует этому последнему решению. Рост истории Git не объявляется устранённым. |
| Историческая база | После уточнения цели полная база остаётся на ПК. В облаке сохраняются ряды актуального анализа, необходимые графикам. |
| Репозиторий и авторизация | Владелец указал `PypsenishAL/Bonds-screener.git` и выбрал HTTPS. Проверка прав записи и фактической ветки остаётся процедурой подключения, а не выдуманным результатом. |
| Локальная папка | Владелец выбрал текущий проект. Комплект `data/published` внутри него утверждён в технической части; отдельного клона приложения не будет. |
| Автоматический сценарий | В утверждённых разделах уточнены `--publish`, `--publish-retry`, состояния попытки и защита Git-операций. Обычный запуск сборщика остаётся совместимым. |
| Дополнительные технические требования | Переносимые хеш-привязки, явный режим данных Streamlit и обработка необязательных источников ЦБ добавлены при чтении кода и утверждены в технической части и подробном плане. Новых внешних зависимостей не вводится. |
| Память и объём | В облаке один текущий комплект. Пик RAM и размер Git измеряются отдельно; локальная история автоматически не обрезается. |

Оставшиеся действия при подключении: проверить remote и ветку, настроить
авторизацию и автора коммитов, подключить Streamlit и провести реальные проверки.
Они перечислены в плане и не являются пропущенными архитектурными решениями.
Goldfish-ревью этого ТЗ не проводилось; финальная сверка его не заменяет.
