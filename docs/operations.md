# MOEX ISS: дневная выгрузка облигаций

Два независимых запуска. `main.py` собирает все дневные записи TQCB за одну
опубликованную торговую дату и формирует существующую итоговую таблицу.
Параллельно загружает кривую бескупонной доходности ЦБ за эту же дату
в отдельную таблицу `cbr_zcyc.csv` и недельную динамику RUONIA в `cbr_ruonia.csv`.
`history.py` пересобирает базу за 180 торговых дат только по отдельной команде.
После этого `main.py` догружает в базу все пропущенные даты и обновляет
отдельную дневную папку только за последнюю опубликованную дату.
Лимита в 20 инструментов больше нет. Параметры `--sample-size` и
`--history-days` из main.py удалены. Собственный Z-spread не рассчитывается.

## Приложение Streamlit

Из папки проекта:

```powershell
python -m pip install -r requirements.txt
python -m streamlit run app.py --server.address 127.0.0.1
```

Откройте адрес, который напечатает Streamlit (обычно `http://localhost:8501`).
В текущем рабочем окружении можно запускать через
`.\.work\streamlit-env\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1`.

Приложение читает завершённые `data/spread_analysis/snapshots/YYYY-MM-DD/`.
Сбор данных и пересчёт выполняются прежними командами проекта, отдельно от
просмотра. После публикации нового анализа обновите страницу.

По умолчанию открывается тёмный интерфейс и список «Выделены анализом».
Он отсортирован по отклонению премии к аналогам от её исторической медианы,
по убыванию; отсутствующие значения идут последними. Доступны все выделенные
бумаги, а не только видимые строки. «Все выпуски» открывает
полную выборку. Режим меняет набор показателей, сохраняя сортировку.
Дата данных и окно видны над списком; окно 90/150 и архив дат находятся
в «Параметры». Поиск и фильтры открываются кнопкой «Фильтры»; пустой список
категорий означает «все». Статусный фильтр действует только во всех выпусках.
Счётчик «Показано N из M» сравнивает текущий список со всем снимком.
Основание отбора и недоступные сравнения показаны отдельно от статуса.
В списке выделенных бумаг статус скрыт по умолчанию. Числа используют запятую,
тонкий пробел в тысячах и знаки у дельт; сортировка работает с исходными числами.
Спарклайн показывает последние 30 сохранённых дат, сохраняя разрывы истории.
При выборе бумаги таблица уплотняется, KPI открываются сразу под её названием.
Выберите строку флажком слева: под таблицей откроется карточка бумаги.
Сверху в ней всегда видна собственная история Z-спреда, снизу — премия
к аналогам, эмитенту или сопоставимой рыночной корзине. Графики имеют общие
даты и масштаб; изменение масштаба не меняет статистическое окно.
Ниже доступны составы корзин, причины исключения, диаграмма «Бумага среди других выпусков»
с инструкцией и выбором бумаги кликом. Её фон сохраняет всю отфильтрованную
выборку независимо от списка выделенных бумаг; также доступна сохранённая КБД ЦБ.
По умолчанию ось спредов ограничена квантилями 1–99%; «Показать все выбросы»
возвращает полный диапазон. Значения не изменяются, скрытые точки учитываются
в подписи; для выбранной точки вне диапазона есть отдельное уведомление.
Рыночная премия по-прежнему относится к сохранённой взвешенной корзине;
линия медиан по дюрации не подменяет этот показатель.

Шрифт Inter загружается локально из `static/fonts/Inter.ttf`; источник —
[Google Fonts](https://github.com/google/fonts/tree/main/ofl/inter), лицензия
сохранена рядом в `OFL.txt`. Интернет для показа шрифта не нужен.

Режимы меняют представление существующих результатов. Статусы кандидатов,
составы аналогов и веса не пересчитываются фильтрами приложения. Числовые
границы коридоров пока не определены в ТЗ: вместо выдуманных полос показаны
сохранённые медианы и явная подпись. Отсутствующие данные обозначаются «—»
с причиной. Дополнительные доходности и купоны берутся только из XLSX,
чьи проверенные байты совпадают с входом выбранного анализа; КБД требует
совпадения даты и успешных сохранённых статусов ЦБ.

Проверки приложения используют временные снимки:

```powershell
python -m unittest tests.test_streamlit_app
```

## Постоянная папка дневных данных

Обычный `python main.py` всегда пишет в **`D:\z\moex_api_probe\data\daily_data`**
(каталог `data/daily_data` рядом со скриптами, независимо от рабочей директории).
Следующий запуск перезаписывает дневные данные в этой же папке; новых
`run_<timestamp>` для дневного сбора не создаётся. `--output` задаёт другую
постоянную папку с теми же правилами перезаписи.

```text
data/daily_data/
  cbr_zcyc.csv                # КБД за общую дату торгов
  cbr_ruonia.csv              # RUONIA за неделю по дату торгов
  daily/
    bonds_daily.csv          # Итоговый отбор облигаций
    bonds_daily.xlsx         # При запуске без --csv-only / --no-daily
    _support/                # Текущая справка Smart-Lab, JSON и превью
  bonds_universe.csv
  day_quotes.csv
  bond_events.csv
  run_manifest.json          # Общая дата, статусы источников и экспорта
  raw_responses/             # Только текущий сбор MOEX
  _support/                  # Только текущие ответы и статусы ЦБ
```

Перед новым **полным** запуском очищаются известные файлы дневного сборщика,
его `raw_responses`, `_support` и `daily`, включая кэш Smart-Lab и прежний
XLSX. Журналы ошибок не дописываются к предыдущим дням. Резервные копии
прежней книги не создаются. При неуспешном новом сборе вчерашние таблицы
не остаются под именами свежих; причина и статус `incomplete` — в новом
manifest. Для приложения нужно проверять статусы manifest перед чтением.

Очистка ограничена известными выходами скриптов: посторонние файлы,
`history_*` и уже созданные архивы `results/run_*` не удаляются автоматически.
Все вычисленные пути проверяются до очистки; ссылки/junction отклоняются.
Если в этой папке уже работает main или отдельный CLI ЦБ/фильтрации,
второй записывающий запуск отклоняется общим `.daily_write.lock`.
После обычного завершения/ошибки lock удаляется; при принудительном
завершении процесса он может остаться — удалять его можно только после
проверки, что прежний процесс больше не работает.

## Один торговый день

```powershell
cd D:\z\moex_api_probe
python -m pip install -r requirements.txt
python main.py
```

Дата определяется по MOEX `/history/engines/stock/markets/bonds/boards/TQCB/dates.json`
с `tradingsession=3`: последняя опубликованная дата полных итогов. Если итогов
за сегодня ещё нет, будет предыдущая опубликованная дата. Выходные и праздники
не определяются календарной догадкой. Дата выводится в терминал, report.md,
run_manifest.json и итоговую таблицу. Это дневные итоги, не внутридневные котировки.

```powershell
python main.py --date 2026-10-27
```

Явная дата без данных не заменяется другой; скрипт сохранит диагностику и
завершится с кодом 2. Неполная пагинация также не считается успешным сбором.

Запрашиваются два массовых эндпоинта со всеми страницами за **одну дату**:

```text
/history/engines/stock/markets/bonds/boards/TQCB/securities.json?date=YYYY-MM-DD&tradingsession=3
/history/engines/stock/markets/bonds/boards/TQCB/yields.json?date=YYYY-MM-DD
```

Имена маршрутов содержат `/history`, но многодневный ряд не загружается.
Сохраняются неликвидные строки с нулём сделок и выпуски, которые уже отсутствуют
в текущем списке. Текущий список TQCB — один снимок для метаданных; его
обновляющиеся marketdata не склеиваются как страницы и не подставляются
в цены за прошлую дату. Охват — TQCB, не все режимы MOEX.

Справки и календари MOEX запрашиваются для фиксированных рублёвых кандидатов.
Smart-Lab — только для кандидатов после базового локального фильтра MOEX.
Число обращений может быть существенно больше прежней выборки из 20 бумаг.
Рейтинг/оферты/субординация и прочие итоговые фильтры сохраняются.

## Итог и параметры

**`<папка запуска>/daily/bonds_daily.xlsx`, лист `Итог`.** Рядом —
`daily/bonds_daily.csv`. В книге есть `Исключены` с причинами и `Поля` с источниками.
Техническая совокупность рынка — bonds_universe.csv, не отфильтрованный итог.

```powershell
python main.py --csv-only
python main.py --no-daily
```

`--csv-only` формирует итоговый CSV без генератора Excel. `--no-daily` сохраняет
данные MOEX, кривую ЦБ и RUONIA, без Smart-Lab и итоговой книги. Другие параметры:
`--secids` (через запятую/пробел), `--output`, `--timeout` (15 секунд),
`--pause` (0.25 секунды). Без --secids берутся все дневные записи TQCB.

Каждый дневной запуск пишет в одну и ту же data/daily_data/ (либо --output),
заменяя предыдущие дневные результаты. Точный путь печатается в терминал.
Дневной запуск сохраняет bonds_universe.csv,
day_quotes.csv, bond_events.csv, fields_availability.csv, report.md,
run_manifest.json, raw_responses/, endpoints_status.csv, errors.jsonl,
pagination.json и schemas_and_samples.json. historical_sample.csv не создаётся.

## Кривая бескупонной доходности ЦБ

`python main.py` автоматически запускает `cbr_zcyc.py` в отдельном потоке,
пока продолжается сбор MOEX. Дата берётся из того же `trade_date`, что и для
итогов торгов и фильтрации, включая явный `--date`. Отдельного расписания нет.
Источник — [таблица Банка России](https://www.cbr.ru/hd_base/zcyc_params/),
обе границы запроса равны выбранной дате.

Результат: **`<папка запуска>/cbr_zcyc.csv`**, отдельный от облигаций CSV
в UTF-8 с BOM, который можно открыть в Excel. В нём 12 строк и три колонки:

| Колонка | Содержание |
|---|---|
| Дата данных | Та же дата, что у MOEX, YYYY-MM-DD |
| Срок до погашения, лет | 0.25, 0.5, 0.75, 1, 2, 3, 5, 7, 10, 15, 20, 30 |
| Доходность, % годовых | Опубликованная доходность; 13.09 означает 13.09%, без деления на 100 |

Это готовые значения кривой, опубликованные ЦБ; интерполяция и расчёт
собственных спредов не выполняются. Статус, точный URL запроса, попытки
и время получения по Москве — в `_support/cbr_zcyc_status.json` и
`run_manifest.json → cbr_zcyc`. Исходный ответ — `_support/cbr_zcyc.html`.
При таймауте, HTTP 429 или 5xx — не более трёх попыток с паузами 1 и 2 секунды.
`--timeout` применяется к каждой попытке обеих загрузок.

Если кривой за эту дату нет, статус — `unavailable`; при ошибке запроса или
формата — `error`. Другая дата не подставляется. Таблица ЦБ при неуспешном
запросе не публикуется, прежняя таблица в этой папке удаляется перед повтором.
Данные MOEX и итоговая фильтрация сохраняются. Код выхода — 4 при проблеме
хотя бы одного источника ЦБ (кривой или RUONIA);
ошибки MOEX/итогового экспорта имеют приоритет и прежние коды 2/3.

Повторить только загрузку ЦБ за дату сохранённого дневного запуска:

```powershell
python -m moex_bonds.sources.cbr_zcyc --input data/daily_data
```

Команда обновляет также `cbr_zcyc` в manifest исходного запуска. Для отдельной
даты без повторной загрузки MOEX:

```powershell
python -m moex_bonds.sources.cbr_zcyc --date 2026-10-27
```

У загрузчика есть `--timeout` и `--output`. Без `--input` и `--output`
результат также пишется в общую `data/daily_data`. При существующем дневном
manifest дата должна совпадать с датой MOEX, а статус сбора быть `ok`.
С `--input` дата берётся из manifest. Загрузчик заменяет только свой CSV,
HTML и статус; остальные источники не очищает. Статус существующего
совпадающего дневного manifest в целевой папке обновляется.

## Недельная динамика RUONIA

При обычном `python main.py` скрипт `cbr_ruonia.py` автоматически работает
в отдельном потоке одновременно с кривой ЦБ и сбором MOEX. Отдельное
расписание не нужно. Источник — [динамика RUONIA ЦБ](https://www.cbr.ru/hd_base/ruonia/dynamics/).

Период — **дата торгов минус 7 календарных дней по дату торгов включительно**,
как недельный интервал на странице ЦБ: например, 19–26 октября для торгов
26 октября. Сохраняются все опубликованные строки этого интервала, а не
фиксированное число наблюдений. Выходные и праздники не заполняются,
данные за более поздние даты ставки не включаются.

Результат — **`<папка запуска>/cbr_ruonia.csv`**, UTF-8 с BOM,
строки по возрастанию даты ставки. Постоянные имена колонок подходят
для pandas/Streamlit; полный словарь с русскими подписями и типами
записан в `_support/cbr_ruonia_status.json → columns`.

| Колонка | Значение |
|---|---|
| `trade_date` | Общая дата торгов MOEX, конец недельного запроса |
| `rate_date` | Дата ставки из ЦБ; ключ наблюдения |
| `ruonia_pct` | Ставка RUONIA, % годовых; 14.04 означает 14.04% |
| `volume_bln_rub` | Объём сделок RUONIA, млрд руб. |
| `trades_count` | Количество сделок, ед. |
| `participants_count` | Количество участников со сделками, ед. |
| `min_rate_pct` | Минимальная процентная ставка, % годовых |
| `p25_rate_pct` | 25-й процентиль ставок, % годовых |
| `p75_rate_pct` | 75-й процентиль ставок, % годовых |
| `max_rate_pct` | Максимальная процентная ставка, % годовых |
| `calculation_status` | Исходный статус расчёта ЦБ |
| `publication_date` | Отдельная дата публикации ЦБ |
| `data_gaps` | Имена отсутствующих полей; значения остаются пустыми |

Это снимок информации, доступной **при загрузке**: дата публикации может
быть позднее даты ставки и даты торгов. Для исторического анализа того,
что было известно на конкретную дату, нужно отдельно учитывать
`publication_date`. Дата ставки не заменяется датой публикации.

Статус — в `run_manifest.json → cbr_ruonia` и
`_support/cbr_ruonia_status.json`; исходный HTML — `_support/cbr_ruonia.html`.
Помимо границ запроса сохраняются `actual_date_from`, `actual_date_to`,
`latest_rate_date` (последняя дата с непустой ставкой), `valid_rate_count`,
`lag_days` и `has_rate_on_trade_date`. Если ставка за последний день ещё
не опубликована, сохраняются доступные строки недели и явный лаг;
интервал не сдвигается и предыдущая ставка не переносится на новую дату.

Нет строк за весь интервал — `unavailable`, ошибка запроса/схемы — `error`.
При ошибке прежний CSV в этой папке удаляется; новая таблица публикуется
только после успешного разбора всего ответа. Повторы, таймаут и общий код
выхода 4 работают аналогично кривой ЦБ. Ошибка RUONIA не останавливает
кривую, MOEX и итоговую фильтрацию. Коды MOEX 2 / экспорта 3 приоритетнее.

Повторить только RUONIA за неделю сохранённого запуска:

```powershell
python -m moex_bonds.sources.cbr_ruonia --input data/daily_data
```

Или задать конец недели явно:

```powershell
python -m moex_bonds.sources.cbr_ruonia --date 2026-10-26
```

Доступны `--timeout` и `--output`. По умолчанию используется общая
`data/daily_data` либо папка `--input`. С `--input` используется `trade_date`
завершённого дневного manifest. Если в целевой папке уже есть дневной
manifest, дата должна совпадать и сбор быть завершён; обновляется только
блок `cbr_ruonia`. Другие источники при таком повторе не очищаются.

Чтение для будущего приложения Streamlit:

```python
from pathlib import Path
import pandas as pd

run_dir = Path(r'D:\z\moex_api_probe\data\daily_data')
ruonia = pd.read_csv(
    run_dir / 'cbr_ruonia.csv',
    parse_dates=['trade_date', 'rate_date', 'publication_date'],
    dtype={'trades_count': 'Int64', 'participants_count': 'Int64'},
)
# График ставки: rate_date по оси X, ruonia_pct по оси Y.
```

## История по отдельному запросу

После обычного дневного сбора с итоговыми фильтрами и Smart-Lab соберите историю:

```powershell
python main.py
python history.py --input data/daily_data --history-days 180
```

История берёт **тот же итоговый отбор**, что ежедневная таблица: российские
рублёвые корпоративные выпуски с фиксированным купоном, рейтингом от BB,
погашением от трёх месяцев, без обнаруженных оферт и субординации.
Общая функция `daily.build_daily` повторно проверяет сохранённые дневные
исходники и справку Smart-Lab; повторные запросы справочников не нужны.
После `--no-daily` сначала нужен `daily.py` для справки итогового отбора.
Можно явно сузить итоговый список:

```powershell
python history.py --input data/daily_data --history-days 180 --secids RU000A10EF52,RU000A10EYV6
```

Конец окна — `trade_date` сохранённого дневного запуска. **180 означает
180 последних опубликованных торговых дат TQCB включительно**, а не год
или 180 календарных дней. Календарь подтверждается небольшими запросами
существования дневной записи по режиму. Проверяются и выходные, поэтому
специальные торговые сессии не теряются. Ошибка сети/схемы не считается
выходным. Затем для каждой бумаги скачиваются интервальные `history` и
`history_yields` с полной пагинацией и проверкой ключей/дат.

По умолчанию работают четыре соединения с независимыми сессиями и журналами;
они переиспользуются для календаря и истории. Число соединений регулирует
`--workers` (1..16), паузу **на соединение** — `--pause`, таймаут — `--timeout`:

```powershell
python history.py --history-days 180 --workers 4 --timeout 60
```

Результат — постоянная отдельная папка **`data/history_data` рядом со скриптами**:

```text
data/history_data/
  bonds_history.csv           # Итоговая база с техническими именами полей
  historical_coverage.csv     # Покрытие первоначальной пересборки
  run_manifest.json           # 180 дат, дата отбора, статус и смысл справочников
  _support/
    historical_sample.csv    # Исходные history/history_yields
    selection.json           # Использованный отбор и справка
    moex/worker_*/           # Полные ответы, пагинация и журнал каждого соединения
```

Ключ базы — `SECID + BOARDID + TRADEDATE`; дата есть в каждой строке.
Поля `ZSPREAD` и `ZSPREADATWAPRICE` сохраняются отдельно без подстановки
`ZSPREADBP`. Показатели формирует общая функция с ежедневным скриптом.
ADV20 в истории появляется только при 20 полных наблюдениях в рублях;
в дневной таблице ради него дополнительные даты не скачиваются.

Даты до первой подтверждённой записи выпуска на TQCB не создаются: новому
выпуску не дорисовывается более длинная история. Первая запись в окне —
консервативная граница доступности, а не утверждение о дате выпуска.
Внутри подтверждённого периода:

- `TRADE_STATUS=traded` — источник подтверждает положительное число сделок.
- `no_trades` — источник явно вернул ноль сделок.
- `no_history_record` — записи бумаги нет в полностью полученной истории;
  число сделок остаётся неизвестным, ноль не придумывается.
- `unknown_trade_count` / `stale_trade_date` — сделки на дату не подтверждены.

Во всех статусах кроме `traded` цена, закрытие, доходность, спреды и дюрация
пусты. НКД/купонные параметры сохраняются только из записи своей даты.
Исходные расчётные значения доступны в `_support`, переноса цен вперёд нет.

Повторный `history.py` **полностью пересобирает собственные файлы** в той же
папке, включая аудит, без вложенных `run_<timestamp>`. Посторонние файлы
не удаляются. Неполная пагинация, ошибка календаря или отсутствие известной
записи на дату исходного дневного запуска дают `status=incomplete` и код 2.
При чтении базы проверяйте `status=ok`.

Дальше достаточно запускать `python main.py`, когда есть возможность.
Скрипт определяет последнюю опубликованную дату MOEX и читает фактические
даты исторического CSV вместе с подтверждённой границей полной синхронизации
`synchronized_through`. Все пропущенные торговые даты до этой даты MOEX
догружаются в общую базу. Например, при границе 26 октября и доступных итогах
за 29 октября скрипт восстановит опубликованные сессии 27–28 октября и
добавит 29 октября. В дневных CSV/XLSX останется **только 29 октября**.

Промежуточные даты не создают отдельных дневных папок и таблиц. Дневные
`bonds_universe.csv`, `day_quotes.csv`, `daily/bonds_daily.csv|xlsx`,
`cbr_zcyc.csv` и `cbr_ruonia.csv` остаются привязаны к последнему дню
(RUONIA — к прежнему недельному окну по этот день). Исторические рыночные
данные и аудит догрузки хранятся в `data/history_data`; CBR/RUONIA за пропущенные
дни заново не собираются.

Догрузка получает полные `history` и `history_yields` по каждой пропущенной
календарной дате в четыре параллельных соединения. Проверяются и выходные,
поэтому специальные торговые сессии учитываются. Только подтверждённые
пустые ответы означают отсутствие сессии; ошибка сети, схемы или пагинации
не считается выходным. Последний день уже собран основным скриптом и
повторно не скачивается. Справка и календари выпусков переиспользуются;
недостающая справка запрашивается один раз на выпуск. Для каждой восстановленной
даты применяется тот же дневной отбор с её датой погашения и текущей
справкой Smart-Lab. Бумаги, встречавшиеся в пропущенные дни, также проверяются,
даже если их уже нет в последнем дневном срезе. До первой подтверждённой
записи нового выпуска строки не создаются.
Полные рыночные таблицы обрабатываются пачками максимум по четыре даты;
сырые таблицы длинного пропуска не накапливаются в памяти целиком.

Повтор той же даты заменяет её целиком, включая удаление бумаг, которые
больше не проходят фильтры; старые даты сохраняются, дубли не появляются.
При явном `main.py --secids ...` восстанавливаются только запрошенные бумаги,
остальные строки базы не удаляются. Такой частичный запуск **не сдвигает
границу полной синхронизации**: следующий полный запуск восстановит весь
рынок за этот интервал. База растёт, старейшие даты не удаляются автоматически.
`--date` остаётся явной верхней границей сбора и синхронизации.

При первом запуске новой версии старый manifest без `synchronized_through`
использует дату первоначальной пересборки `selection_date`. Это позволяет
исправить пропуски, оставшиеся между последующими добавленными датами старой
версии. Полный запуск переводит границу только после успешного получения
всех дат; при сетевом сбое CSV и граница базы остаются прежними, поэтому
следующий запуск повторит недостающий интервал. Дневная таблица последнего
дня при этом всё равно формируется с `history_update.status=error` и кодом 5.
Незавершённая текущая справка или календарь также блокируют подтверждение
полной синхронизации: временное исключение бумаги из-за сетевого сбоя
не должно превращаться в окончательный пропуск её истории.

Аудит последней догрузки — `data/history_data/_support/daily_sync/`: исходные
ответы и журнал каждого соединения, `coverage.json` с датами и числом строк.
Этот служебный каталог перезаписывается; копии дневных CSV/XLSX за прошлые
дни не накапливаются. `sync_reference.json` сохраняет использованные справки
с их исходными timestamp. `historical_coverage.csv` описывает первоначальную
пересборку, а manifest содержит календарь актуализированной базы.

До первой инициализации базы ежедневный скрипт работает как раньше и пишет
`history_update.status=not_initialized`; полное окно 180 дней по-прежнему
создаётся отдельной командой `history.py`.

Для другой папки задавайте одинаковый путь в обоих скриптах:

```powershell
python history.py --output D:\z\bond_history
python main.py --history-output D:\z\bond_history
```

История и дневная папка не должны быть вложены друг в друга. Общие блокировки
защищают исходники и базу от одновременной записи. CSV публикуется через
временный файл; неуспешная публикация не оставляет успешный статус.
Если базу обновить не удалось (например, CSV открыт в Excel), дневная таблица
всё равно формируется, в её метаданных будет `history_update.status=error`,
код main/daily — 5. Если manifest базы остался в незавершённом состоянии,
устраните причину и пересоберите `history.py`.

Исторический состав — **текущий отбор**, а рейтинг, сектор и эмитент —
сохранённая текущая справка с timestamp, не исторические значения на каждую
дату. Такая база не является выборкой рынка без смещения выживших бумаг.

## Сохраняющиеся фильтры и смысл полей

Фильтры:

- RU ISIN + тип `corporate_bond`/`exchange_bond`; номинал и расчёты RUB/SUR.
  Это проверка российского выпуска; резидентство эмитента независимо не проверяется.
- Точное `securities.BONDTYPE = Облигация с фиксированным (известным) купоном`.
  Амортизируемые выпуски с отдельным BONDTYPE автоматически не признаются фиксированными.
- Рейтинг BB включительно; BB- исключается. Обозначения ru/(RU)/.ru
  нормализуются без изменения исходного рейтинга; при нескольких берётся низший.
  Нераспознанные/отозванные рейтинги не проходят.
- Погашение не ранее даты данных + **3 календарных месяца**.
- Любые обнаруженные оферты/put/call (в том числе прошлые) исключаются:
  даты всех сохранённых источников, история, полный календарь offers,
  BONDSUBTYPE и карточка Smart-Lab. Неполный календарь не означает отсутствие оферт.
- Обнаруженная субординация исключается по явным флагам, типам, названию,
  описанию выпуска и заголовку Smart-Lab. Проверка ограничена раскрытыми полями;
  полного юридического анализа условий выпуска нет.
- Отсутствующие рейтинг, сектор или распознаваемый эмитент не додумываются:
  бумага попадает в `Исключены` с причиной.


Рыночные поля используют одну дату и режим. Полная сессия = 3; разные режимы и
сессии не суммируются. YTM допускается только при YIELDDATETYPE=MATDATE,
совпадении даты погашения, свежей TRADEMOMENT и совпадающей WAPRICE. НКД —
дневной history.ACCINT, не текущий ACCRUEDINT. ZSPREAD/ZSPREADATWAPRICE — п.п.;
ZSPREADBP не подставляется вместо них. GSPREADBP — б.п. по PRICE строки yields,
не обязательно по WAPRICE. Дюрация биржевая в днях; годы = дни/365,
не модифицированная. Пропуски не заменяются нулями.

Рейтинг, сектор и эмитент получаются через штатный поиск Smart-Lab по SECID
(POST `/bonds/ajaxsearch/`, параметры value/json/forums), затем из точной
карточки. Эмитент — из h1 после «Облигация», без распознанного кода серии.
Это **текущая справка**, а не доказанный исторический рейтинг на дату торгов;
в каждой строке есть время получения по Москве и ссылка. Ответы и журнал
хранятся в `daily/_support/smartlab_raw` и `daily/_support/smartlab_requests.json`.
Все служебные JSON и превью находятся в `_support`; наверху `daily` — только
два итоговых формата одной таблицы.


При явной прошлой дате справки MOEX/Smart-Lab остаются текущими метаданными,
а не подтверждённым историческим рейтингом/описанием выпуска.

Повторно сформировать итог по сохранённым данным MOEX:

```powershell
python -m moex_bonds.collection.daily --input data/daily_data --csv-only
```

Для нового запуска daily.py берёт сохранённую trade_date без повторного сдвига
на предыдущий день. Прежние аудитные папки с bonds_sample.csv и
historical_sample.csv поддерживаются по старым правилам PREVDATE/--as-of.
--reuse-smartlab явно использует сохранённую справку с прежним timestamp;
по умолчанию Smart-Lab запрашивается заново.

Для XLSX нужен @oai/artifact-tool в bundled runtime Codex либо BONDS_NODE и
BONDS_NODE_MODULES. Если генератора нет, используйте --csv-only. При ошибке
XLSX CSV/JSON сохраняются, код возврата 3; создание книги не объявляется успешным.

## Проверка

Python 3.11+, requests, pandas, beautifulsoup4; tzdata для Windows.
CSV имеют UTF-8 BOM для Excel. Код 0 — сбор и запрошенный экспорт завершены;
2 — данных нет/неполная выгрузка; 3 — ошибка итогового экспорта. Ошибки
аргументов или исходной папки также дают ненулевой код. HTTP-статусы, пустые
ответы и сетевые ошибки записываются в журнал раздельно.

```powershell
python -m unittest discover -s tests -t . -v
```

Тесты проверяют сбор более 20 выпусков, одну дату, раздельный запуск истории,
пагинацию и прежние фильтры. Все тестовые результаты — во временных каталогах,
не в results/. Реальный запуск новой версии выполняется локально с доступом
к ISS без мешающего VPN.

Официальные маршруты: [итоги за дату](https://iss.moex.com/iss/reference/491),
[доходности за дату](https://iss.moex.com/iss/reference/443),
[интервал опубликованных дат](https://iss.moex.com/iss/reference/503).

## Сравнение Z-спредов через корзины аналогов

Отдельный расчёт по готовой дневной выгрузке и существующей исторической базе:

```powershell
cd D:\z\moex_api_probe
python analyze_spreads.py
```

По умолчанию читаются `data/daily_data/daily/bonds_daily.xlsx` и
`data/history_data/bonds_history.csv`; результат — `data/spread_analysis/`.
Имена файлов произвольные, в том числе из ТЗ:

```powershell
python analyze_spreads.py --daily "путь\bonds_daily(1).xlsx" --history "путь\bonds_history(1).csv" --output data/spread_analysis --date 2026-10-27
```

`--date` необязателен: дата определяется по единственному `TRADEDATE`
дневной выгрузки. Явная дата обязана совпасть. Заголовок листа `Итог`
находится по `SECID`, русские поля сопоставляются по листу `Поля`.
Лист `Исключены` не читается. Все выпуски из `Итог` остаются в сводке.

Расчёт не вызывает `main.py`, `history.py`, Smart-Lab или ISS и не меняет
исходные файлы. Сначала выбираются сегодняшние аналоги и веса, затем
пакетно запрашиваются нужные поля истории через `history_storage.HistoryReader`.
Для отсутствующего дневного ADV нужен предварительный пакетный запрос:
готовый ADV на дату либо последние 20 конечных `VALUE_RUB` не позднее неё.
Явные нули учитываются, пропуски пропускаются, менее 20 значений недостаточно.
В результатах сохранены источник ADV, число значений и дата последнего оборота.
Для готового дневного ADV происхождение отдельных оборотов неизвестно,
поэтому дата последнего использованного оборота остаётся пустой.
Кешированные запросы повторно не читают CSV; обычный запуск делает два
прохода базы, а не отдельный проход для каждой бумаги. Дневные и исторические
исходные наблюдения в единую таблицу не объединяются.

Настройки — `config/spread_config.json`; `--config custom.json` переопределяет
указанные ключи. Параметры текущего запуска целиком сохраняются в манифесте:

| Параметр | Начальное значение и смысл |
|---|---|
| `temperature` | `1`; температура softmax отрицательных расстояний |
| `duration_unit_years` | `0.5`; масштаб разницы биржевой дюрации |
| `baskets.issuer` | aR/aD/aS/aL = 0/1/0/0.25; тот же эмитент, ΔD ≤1, до 10 |
| `baskets.peers` | 1.5/1/0.75/0.25; другой эмитент, Δrating ≤1, ΔD ≤1.5, до 10 |
| `baskets.market` | 1.5/1/0/0; другой эмитент, Δrating ≤1, ΔD ≤1.5, все |
| `windows` | `[90, 150]` предыдущих опубликованных торговых дат |
| `min_observations` | `30` пригодных наблюдений в окне |
| `classification.primary_window` | `90`; основное окно, явно присутствующее в `windows` |
| `classification.percentile_threshold` | `90`; аномалия требует строго большего процентиля |
| `classification.min_ordinary_observations` | `60`; минимум для обычной оценки, отдельно от описательного минимума 30 |
| `classification.robust_score_threshold` | `3.5`; дополнительная аномалия при score не ниже порога, без модуля |
| `min_weight_coverage` | `0.8` исходного веса исторической корзины |
| `mad_scale` | `1.4826`; `robust_score = excess / (mad_scale × MAD)` |
| `issuer_aliases` | Явные эквивалентные названия, без fuzzy matching |
| `structured_issuers`, `structured_secids` | Явные структурные продукты; исключены из корзин, собственная история разрешена |

Для `peers`/`market` допускаются несколько выпусков одного внешнего эмитента;
ближайшие выбираются по расстоянию, равенство разрешается сортировкой по `SECID`. Ограничения не
расширяются. При неположительном/отсутствующем ADV ликвидностное слагаемое
опускается с флагом; отсутствующий обязательный признак исключает кандидата.
Рейтинг нужен там, где используется расстояние/ограничение по рейтингу,
сектор — где используется секторное слагаемое. Ступени рейтинга нормализуются
без угадывания неизвестных значений. Отрицательный спред допустим.

Aliases проверены по уже сохранённому MOEX `description.EMITTER_ID`:

| EMITTER_ID | Явно объединённые названия |
|---:|---|
| 712 | РЖД → РЖД ОАО |
| 1122 | ТГК-14 → ПАО "ТГК-14" |
| 323 | ПАО "ПСБ" → Промсвязьбанк |
| 15196 | iКаршеринг Руссия → Каршеринг Руссия |
| 484 | СберИОС → Сбербанк ПАО |

Этот справочный аудит не добавляет ещё один источник в запуск анализа.
Признак структурного продукта проверяется по исходному имени до aliases:
объединение эмитента СберИОС не исключает обычные бумаги Сбербанка.
Исходные названия и время справки сохранены. `СберИОС` и
`Инвестиционные облигации` явно изолированы; список дополняется в конфиге
при подтверждении других продуктов. Название `СФО` само по себе не
используется как достаточное доказательство структурного продукта.

Используется только `z_bps = ZSPREADATWAPRICE × 100` (`0.76 → 76 б.п.`),
подмена на ZSPREAD/GSPREADBP отсутствует. Для спреда нужны `TRADE_STATUS=traded`
и положительный конечный `NUMTRADES`; для корзин дополнительно положительная
дюрация. Нет переноса через дни без сделок. `N_eff = 1 / Σw²`.

В истории состав и веса фиксируются на дату текущего расчёта. При покрытии
не менее 80% доступные веса перенормируются; при меньшем покрытии — пропуск.
`self` анализирует сам спред, остальные направления — премию к корзине.
Среднее, медиана, excess, процентиль и robust_score считаются по пригодным
наблюдениям внутри предыдущих 90/150 торговых дат, текущая дата исключена.
Процентиль: `100 × (число меньших + 0.5 × число равных) / n_obs`.
MAD — медиана абсолютных отклонений от исторической медианы. При MAD=0
пусты robust_score, robust_anomaly и общее основание; процентильная оценка сохраняется. При истории короче 30 наблюдений все исторические
оценки пусты, но `n_obs` сохранено. Исторические среднее/медиана собственной
бумаги могут быть доступны даже при отсутствующем текущем спреде; excess и
процентиль при этом пусты. Изменение за день требует показатель именно за
предыдущую торговую дату, без перескакивания через пропуски.

Аномалия (`upper_tail_anomaly=true`) требует одновременно `P > 90` и текущего
показателя выше исторической медианы, минимум 60 наблюдений, доступный текущий
показатель и подтверждённый календарь. Ровно 90 недостаточно; сравнения выполняются
до округления. `assessment_status`: `evaluated` — обычная оценка true/false;
`provisional` — 30–59 наблюдений, статистика сохранена, обычная оценка пустая;
`unavailable` — недостаточно данных, текущего показателя или подтверждения календаря.
Числа переопределяются через `--config`: все окна оцениваются независимо,
основное берётся из `classification.primary_window`, а не порядка `windows`.

Кандидат — хотя бы одно из `issuer`/`peers` с обычной аномалией, положительной
текущей премией и минимум двумя участниками **той же** корзины. Один аналог
(`evidence_status=paired`) даёт парную статистику и пустую квалификацию кандидата;
два и более — `basket`, отсутствие — `no_basket`; для self — `self`.
`self` и `market` поясняют результат. Порогов по excess или N_eff нет.
Дополнительный `robust_anomaly` требует `robust_score ≥ 3.5` при обычной оценке
и конечном score. `anomaly_basis`: `percentile_only`, `robust_only`, `both`, `none`;
если хотя бы одна проверка недоступна — пустое поле. Один robust-сигнал не создаёт
кандидата; недоступный robust score не отменяет процентильную квалификацию.
Оба новых поля сохраняются в metrics и summary по каждому направлению и окну.
Положительный issuer не подтверждает дешевизну к внешним аналогам.

В `summary.csv` поля `candidate_status`, `candidate_basis` и
`candidate_incomplete_directions` отражают основное окно. Статусы: `candidate` —
подходит issuer или peers; `not_candidate` — оба проверены и не подходят;
`not_fully_assessed` — положительной квалификации нет, хотя бы одна оценка пустая.
Основание и неполные направления перечислены через `;` в порядке issuer, peers.
Каждое окно имеет свои `candidate__{window}__status`, `__basis`,
`__incomplete_directions`; результаты сравнений — `{comparison}__{window}__{field}`,
качество корзины — `{comparison}__evidence_status`. Окна не голосуют за результат.

`basket_composition_differs_from_current` в `quality_flags` предупреждает:
внутри данного окна есть пригодные наблюдения с неполным составом выбранной
сегодня корзины. Покрытие и перенормирование весов сохраняют прежнее правило.

Календарь берётся из существующего исторического `run_manifest.json`,
при его отсутствии — из реально представленных дат соответствующего режима
в CSV. Будни и праздники не достраиваются. Если календарь не подтверждён
до даты анализа, текущие сравнения сохраняются, исторические оценки и
изменение за день пусты с причиной `calendar_not_confirmed_through_analysis_date`.
Для CSV без манифеста невозможно обнаружить торговую дату, отсутствующую
во всей базе; источник календаря явно указан в отчёте. Рейтинги и состав
выборки текущие, это не point-in-time реконструкция рынка.

Результаты:

| Файл | Содержание |
|---|---|
| `summary.csv` | Главная сводка текущего запуска: одна строка на SECID, группы self/issuer/peers/market |
| `basket_members.csv` | Выбранные аналоги, компоненты расстояния, веса, признаки и флаги |
| `comparison_history.csv` | Ряды за максимальное окно и текущий день; покрытие и число доступных участников |

Кроме текущей `summary.csv`, верхние таблицы сохраняют результаты разных дат.
Повторный запуск заменяет весь раздел совпадающей даты, включая удалённых
участников корзин, и не создаёт дублей. Старые дневные сводки остаются в
`snapshots/`. Ключи результатов записаны в `run_manifest.json`.
Исходные файлы и их родительские папки нельзя выбирать папкой результата.
CSV имеют UTF-8 BOM, пропуски чисел — пустые ячейки. Публикация защищена
блокировкой; файлы заменяются по отдельности атомарно, общий манифест
получает `status=ok` только после завершения всех замен. При чтении набора
из нескольких таблиц проверяйте этот статус и отсутствие `.daily_write.lock`.

Новые строки имеют `analysis_run_id`, `classification_rule_version=upper_tail_midrank_robust_v2`
и `result_schema_version=3`. Приложение продолжает читать старые схемы 1 и 2,
показывая новый критерий как «Не сохранено». Манифест сохраняет фактический конфиг, SHA-256 реализации
и входов, включая использованный исторический манифест и файлы настроек.
Версию строки другой даты определяет `snapshots/{analysis_date}/run_manifest.json`,
а не корневой манифест последнего запуска. Старые строки metrics/basket_members/
comparison_history сохраняются с пустыми новыми полями до явного пересчёта;
старые снимки не переписываются при расчёте другой даты. В CSV логические
значения — `true`, `false` или пустое поле; в JSON отсутствие — `null`.

## История восстановления собственного Z-спреда

Расчёт выполняется в `analyze_spreads.py` независимо от источника текущего сигнала.
Карточка в режиме «Торговля» читает уже сохранённые результаты; режим
«Инвестирование» не получает автоматического штрафа за их отсутствие.

Настройки `recovery` в `config/spread_config.json`: `reference_window=90` опубликованных
торговых дат, `min_observations=60`, `entry_scale=1`, `recovery_fraction=0.5`,
`horizon_months=3`. Явный `--config` переопределяет эти значения; фактический
конфиг сохраняется в манифесте и используется в подписях карточки.

Обычный уровень — медиана предыдущих 90 дат; масштаб разброса — `1.4826 × MAD`.
Начало расширения требует перехода из состояния ниже порога в состояние
`Z − медиана >= entry_scale × масштаб` на двух соседних пригодных торговых датах.
Для восстановления достаточно сужения на половину **начального** расширения
за три календарных месяца. Ориентир и цель фиксируются при входе, будущий пик
не используется. `P > 90` для этих случаев не требуется. Нулевой MAD или
ненаблюдаемое начало не создают новый случай. Повторный вход возможен после
наблюдаемого `Z <=` зафиксированной медианы; истечение срока само по себе
не начинает новое расширение.

В `summary.csv` добавлены поля `recovery__status`, `recovery__reason`,
`recovery__n_known`, `recovery__n_recovered`, `recovery__n_pending`,
`recovery__n_incomplete`, `recovery__share`, `recovery__median_reduction_bps`,
`recovery__median_days`, `recovery__median_worsening_bps`. Доля — число от 0 до 1;
при отсутствии известных результатов доля и медианы пусты. Сужение к концу
срока и дальнейшее расширение учитывают также неудачные случаи; время
восстановления — только успешные. Отрицательное сужение сохраняется.

`recovery_episodes.csv` имеет ключ `analysis_date + SECID + BOARDID + entry_date`.
Сохраняются ориентир и масштаб (`reference_bps`, `scale_bps`, `reference_n_obs`),
начальный спред/расширение и цель (`entry_z_bps`, `initial_excess_bps`,
`initial_excess_scales`, `target_bps`), срок и конечное наблюдение (`horizon_end`,
`end_observation_date`, `end_z_bps`, `reduction_bps`), восстановление
(`first_recovery_date`, `hit_timing`, `days_to_recovery`), дополнительное ухудшение
(`max_worsening_bps`), покрытие (`n_expected`, `n_valid`) и `outcome`, `reason`.
Строки и манифест содержат `recovery_rule_version=own_spread_recovery_v1`.

Статусы случая: `recovered`, `not_recovered`, `pending`, `incomplete`. В долю
входят только случаи с истёкшим сроком и полным рядом последующих торговых дат.
Пропуски не заменяются значениями. Восстановление после пропуска сохраняется
как наблюдаемое, но его точное время пусто (`hit_timing=after_gap`). Неизвестная
дата погашения или погашение внутри горизонта делают случай неполным.

Статусы бумаги: `available`, `no_known_outcomes`, `no_cases`, `unavailable`.
Причины перечисляются через `;`. Неподтверждённый календарь даёт
`calendar_unconfirmed`, а повреждённая/незавершённая историческая база по-прежнему
останавливает весь анализ. Текущая дневная строка заменяет строку той же даты
только в рабочей копии, включая недоступный спред; расхождения считаются в отчёте.
Старые снимки без метаданных восстановления открываются с подписью
«История восстановления не рассчитана».

Порядок изменения: расчёт → выгрузки → проверка сохранённых таблиц → карточка.
Проверка: `python -m pytest -q tests/test_spread_recovery.py tests/test_spread_analysis.py tests/test_spread_classification.py tests/test_streamlit_app.py`.

## Если не определяется торговая дата

`ReadTimeout` вместе с «HTTP-ответ не получен» означает, что соединение с ISS
не вернуло ответ в пределах таймаута. Это не отсутствие торговой даты и не
доказательство неправильного формата JSON. Подробности сохраняются в
endpoints_status.csv/errors.jsonl, включая адрес запроса и повторную попытку.
Проверьте доступ без VPN; при медленном соединении можно увеличить таймаут:

```powershell
python main.py --timeout 60
```

`--date YYYY-MM-DD` пропускает только автоматическое определение даты.
Остальные запросы к ISS по-прежнему требуют рабочего соединения.
HTTP 403/404 и HTTP 200 с пустой/неожиданной секцией показываются отдельно.


## GitHub publication

`python main.py --publish` runs collection, history synchronization, analysis,
bundle validation and Git push. `python main.py --publish-retry` retries a saved
attempt without collection. Plain `main.py` keeps its original behavior.

The remote is https://github.com/PypsenishAL/Bonds-screener.git, configured in
`config/github_publish.json`. First configure the current directory as a Git
checkout tracking remote main, set the commit author, and sign into GitHub with
Git Credential Manager through your browser. Scheduled runs must use that same
Windows account. No token belongs in this project. The first code/data commit
must be reviewed separately; daily runs only stage `data/published`.

Full history, audit and prior local analysis snapshots remain local. Only the
current UI bundle is placed in `data/published`. Previous Git commits still
occupy repository storage. Dirty tracked code, unrelated staged changes or a
diverged remote stop delivery. Do not use force push to resolve this.

For Community Cloud select this repository, actual branch and `app.py`, and add
`BONDS_DATA_MODE = "published"` in app secrets. Locally the environment variable
of the same name takes precedence; default is `local`. Published mode validates
all bundle bytes and never falls back to raw local data. Dependencies are in
`requirements.txt`; collection/XLSX generation never run on the cloud server.

Pending state and diagnostics: `.work/publication/state.json` and
`.work/publication/last_result.json`. Exit codes: 20 setup, 21 collection/history,
22 analysis/bundle, 23 Git delivery, 24 lock contention. On lost push response
retry checks remote commit identity. An abandoned lock requires manual PID
inspection before removing it. Never delete source data to repair a delivery.

Tests: `python -m unittest discover -s tests -t .`. Offline tests do not prove
real write access, Linux peak RAM, or Community Cloud availability.
